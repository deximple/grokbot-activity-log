# grokbot-activity-log audit — 2026-11-16

Scope: `gblog.py` 0.5.0, `bin/gblog`, `install.sh`, `.github/workflows/ci.yml`, `README.md`, both `SKILL.md` files, `docs/routine-daily-audit.md`, `docs/chain-repair-live-apply.md`, `tests/*.py`, `tests/fixtures/kim-biseo-break/*`.

Method: static, adversarial read. Nothing was executed, so every finding is derived from the code path quoted as evidence (function name plus exact snippet, no line numbers). Files the README links but that were not supplied (`LICENSE`, `docs/bot-description.md`, `docs/routine-weekly-tune.md`, `docs/marketplace.md`, `docs/bot-template.md`) were not reviewed.

## 1. Executive summary

- **A forged `break_ack` turns a deleted or rewritten history into PASS.** `verify` accepts any single self-consistent `break_ack` on any chain; the kim-biseo pin is enforced only in `seal_break`, not at verification. One `Ledger.append()` call launders a deletion of any run of records, or a rewrite of the whole prefix, into `PASS (1 approved break)` with exit 0 (F-01).
- **Truncation and rollback are invisible once state is gone.** `sed -i '$d'` on the log plus `rm state/<bot>.json` verifies `OK`. Anchors are written but never compared with anything, and a deleted chain simply vanishes from `verify --all` (F-02).
- **The daily report is wrong for idle Bots.** `iter_records(files=[])` falls back to all files, so `gblog report --date D` includes the entire history of every Bot that has no log file for D (F-03).
- **`--ts` is unvalidated.** It becomes a file name (`--ts /tmp/x` appends to `/tmp/x.jsonl`), and any past or future value, or a clock step backwards, leaves the chain permanently FAIL (F-04).
- **A benign crash bricks a chain.** If the process dies (or the disk fills) between the fsynced log line and the state replace, every later append exits 4. There is no supported repair: the spool is write-only and the alert file is never cleared (F-05).
- **`verify --bot` can report a false OK.** It does not resolve aliases, and a typo prints `OK … 0 records  head genesis` with exit 0 (F-06).
- **One malformed line crashes everything.** A non-object JSON line, an invalid UTF-8 byte or a lone surrogate produces a traceback in `verify`, `report`, `status` and `append`, and in `append` the event is lost without being spooled (F-07).
- **Redaction misses the most common shapes.** `DB_PASSWORD=…`, `AWS_SECRET_ACCESS_KEY=…`, JSON `"password": "…"`, `--password value`, Basic auth and Stripe/GitLab keys pass through; the README overclaims (F-08).
- **Agents lose records to CLI friction.** `task-end --summary` exits 2 and writes nothing; `task-end`, `note` and `approval` ignore `$GBLOG_TASK`; `--bot` means four different things across commands (F-09, F-14).
- **Tests, CI and install have their own gaps.** One test attempts a real `git push` to github.com, another reads the developer's real browser history, and the chain-repair tests only pass after 2026-11-02. CI has no macOS job, no install test and no hook lint, and `curl | bash` installs whatever `gblog.py` sits in the current directory (F-22, F-23, F-33).

## 3. Detailed findings

**F-01 — Unpinned, unauthenticated `break_ack`.** `seal_break` enforces the kim-biseo coordinates, but `verify` only requires exactly one ack whose descriptor equals an on-disk join.
- `_break_shape_ok` allows any `seq_after > seq_before`, so a run of any length can be deleted. It also allows an empty `missing_seqs`, so a prev mismatch between consecutive seqs is approvable; that covers a rewritten prefix.
- Attack: delete lines in one day file, or rewrite records 1..N, then call `gblog.Ledger(root).append(bot, {"type": "break_ack", "jay_approval_id": "x", "break": {...}})`. Verify returns `ok=True`.
- README's "any other break is still FAIL" is false.
- Fix (I-01): honour an ack only when the bot and descriptor equal the pinned incident, or the existing temp-copy fixture rule applies. Any other ack is itself a problem.

**F-02 — Truncation, rollback and deletion.** State is the only tail witness and sits beside the log.
- Missing or corrupt state reads as genesis and is whitelisted by the head check. `append` then adopts the truncated tail via `_tail_head`.
- `anchor()` records heads and `resumed_from`, but no code checks that an anchored head still exists.
- `verify --all` enumerates `logs/` only. A removed chain, or a removed ledger root, exits 0.
- Fix (I-02): add verify warnings for missing/reset state, an anchor containment check, an append-only anchor history, a missing-chain check and `verify --contains HASH`. Have the daily routine post heads into the conversation as an off-box anchor (I-36).

**F-03 — Empty file list falls back to all files.** In `records()`, the `date` filter produces `[]` for a Bot with no file that day. `iter_records` treats `[]` as "not given". The `date` branch has no per-record filter, so every record of that Bot is returned. The `since` branch is masked by its timestamp filter. Fix (I-03).

**F-04 — `--ts`.** There is no format check.
- `today(ts)` slices 10 characters into the path, so `../../../a` or `/tmp/x` escapes the root. The same applies to `archive/<bot>/<day>/`.
- After such an append, state points at a record the tail scan cannot see, so every later append exits 4.
- A valid but earlier `--ts` lands in an earlier-sorting file (verify fails at the first record) or trips "timestamp goes backwards". A future `--ts` breaks every later record. A VM clock step back does the same with no flag at all.
- Fix (I-04): strict parse and normalise, monotonic rule under the lock, future bound in the CLI, date validation for `report`/`export`.

**F-05 — Crash window and missing recovery tooling.** The docstring is right that state cannot get ahead inside `append`. State can get behind, though: a kill or `ENOSPC` in `write_state` after the line is durable. The tail check treats that as tampering. The only way out today is hand-editing state, which the docs forbid and the test itself does via `write_state`. Spool files are never listed or replayed, and `state/<bot>.alert.json` is permanent, so the routine pages forever. Fix (I-05).

**F-06 — False OK.** Write commands resolve aliases; `verify` does not. `verify --bot "Chief of Staff"` checks the non-existent `Chief-of-Staff` and prints OK. SKILL.md tells Bots that `gblog verify --bot "$BOT"` "must exit 0". Fix (I-06).

**F-07 — Crash paths.**
- A line `[]` or `123` gives `AttributeError`/`TypeError` in `verify`, `records` and `_assert_tail_matches`.
- Invalid UTF-8 raises `UnicodeDecodeError` in every reader.
- argv bytes decoded with surrogateescape make `canonical()` raise in `append`. The shell hook hides this with `|| true`.
- A crafted, hash-valid record with a non-string `ts` or non-numeric `seq` crashes the comparison and sort code.
- A non-dict `state/<bot>.json` crashes `append`.
- Fix (I-07): treat all of these as corrupt (FAIL or spool), never a traceback.

**F-08 — Redaction.** Confirmed misses by pattern reading:
- `DB_PASSWORD=hunter2hunter2` and `AWS_SECRET_ACCESS_KEY=…` (no `\b` next to `_`).
- `{"password": "…"}` (the quote sits between key and colon).
- `--password value`.
- `password="my dog spot"` (the first token is under 6 characters, so nothing is redacted); `password="correct horse battery"` is redacted only up to the first space.
- `Authorization: Basic …`, `sk_live_…`, `glpat-…`, `npm_…`, `ya29.…`, Slack webhook URLs.

This matters most for the shell hook (verbatim commands) and for `archive` of JSONL transcripts. Fix (I-08) is additive patterns; the docs must stop saying secrets "are scrubbed before they touch disk" without qualification (I-33).

**F-09 — Agent-hostile flags.**
- `--summary` is rejected with exit 2, so no `task_end` is written, the task stays open, and tune later blames logging discipline.
- `log` and `archive` honour `$GBLOG_TASK`; `task-end`, `note` and `approval` do not, although the SKILL tells Bots to export it.
- `task-end` with no id silently writes an orphan record.
- `--outcome success` or `done` is rejected.
- `status` has no `--bot`, and `--root` is only accepted before the subcommand.
- Fix (I-13).

**F-10 — Genesis state written over a live chain.** `sync` stamps `last_sync` into `read_state()`'s default when the state file is absent and creates `{"seq": 0, "head": "genesis", …}`. The next append takes the "state exists" branch, compares the tail with seq 0, and refuses. Missing state is the documented self-heal path, so a sync before the next append converts a recoverable situation into exit 4. Fix (I-09).

**F-11 — Unlocked verify.** If an append lands between reading the log and reading state, the state head is not `final_head` and verify reports FAIL. A reader can also see a half-written last line. The daily routine runs verify while other Bots and the shell hook write. Fix (I-10): shared flock around the snapshot.

**F-12 — One refusal aborts the loop.** `verify --all --record` and `sync` let `TailMismatchError` propagate. Later chains are not verified. A mismatch on the sync bot's chain means nothing is committed, which contradicts the routine's "continue to the sync step so anchors, spool and alert files are backed up". Fix (I-11).

**F-13 — Public-remote guard.**
- Unknown visibility for a github.com remote (HTTP 403 rate limit, timeout) only warns and then pushes.
- The regex matches `evilgithub.com/o/r`, and the API 404 is then reported as "private".
- `remote.origin.pushurl` is not inspected.
- The refusal text is printed to stdout with the raw origin URL, which may contain userinfo.
- Fix (I-12).

**F-14 — `--bot` semantics.**

| Commands | Treatment of `--bot` |
|---|---|
| `task-start`, `log`, `approval`, `task-end`, `note`, `archive`, `capture` | `_resolve_bot`: alias → slug, with warning or strict refusal |
| `report`, `tail`, `coverage`, `tune` | `canonical()`: merged, no warning |
| `export` | `safe_name()` first (mangles display names), then merged |
| `verify`, `anchor`, `seal`, `sync` | `safe_name()` only, exact chain |
| `status` | no `--bot` flag |

Fix (I-06, I-13): one resolver everywhere except `seal`.

**F-15 — Status.** `ledger.records(c)` expands `c` to all chains of its slug, so the comprehension loads the merged set once per chain. `today` is inflated, and `--chains` shows merged numbers on every row. Open tasks are computed over 7 days only. `week` uses the local date while `today()` is UTC. Fix (I-14).

**F-16 — UTC days versus local routine time.** Files and `report` default to the UTC date. A 23:50-local routine in UTC+9 writes the report for UTC day D at 14:50Z and never again, so 14:50–24:00Z is unreported. UTC−8 loses 07:50–24:00Z. Fix: `--date yesterday` (I-15) and routine text that regenerates yesterday's UTC report (I-36).

**F-17 — Browser capture.**
- `utcnow().timestamp()` interprets naive UTC as local time. In UTC−8 a 24 h window becomes 16 h.
- Because `since = max(marker, cutoff)`, the skipped hours are never recovered. The same `max` drops everything older than `--hours` after a missed day, even though the marker knows where it stopped.
- `except (sqlite3.Error, OSError): continue` hides unreadable profiles, and the summary still counts them.
- README says "host/path only" but the page title is stored in `detail`.
- On the shared computer every Bot's capture imports the same visits.
- Fix (I-16, I-33).

**F-18 — File capture.**
- The snapshot is replaced before the appends. If an append then fails (exit 4, crash), those changes are never logged.
- The snapshot write is not atomic, and a corrupt snapshot crashes every later run.
- The snapshot is keyed by bot, not by path. `--path /a` followed by `--path /b` logs everything as deleted and created.
- A missing path logs mass deletions.
- `startswith(ledger.root)` also skips `/workspace/activity-log-old`.
- The snapshot (every file name under `/workspace`) is committed by `sync`.
- Fix (I-17, I-22).

**F-19 — Tune loop.**
- Proposal ids are stable, but `analyze` never consults earlier `tune` records. Applied and rejected proposals come back every week.
- `--apply X --reject Y` records X as rejected.
- `task-start` has no `--source`, so the "manual repeats" detector counts routine runs and proposes turning the daily audit into a routine.
- `tune --bot A` overwrites `proposals.json`, invalidating ids from the all-Bots report.
- Fix (I-13, I-18).

**F-20 — Untrusted text in agent-read Markdown.** Auto-captured page titles, shell commands and free-text details are concatenated into `reports/*.md` and `tuning/*.md` with no neutralisation. Newlines can forge headings and list items. The tune report explicitly asks a Bot to persist note text to memory or a description. A hostile page title is therefore an injection path into the weekly loop, gated only by user approval. Fix (I-15, I-34).

**F-21 — Seal mechanics.**
- The ack is appended before the `ledger` witness. If the witness append hits a tail mismatch, the CLI exits 4 with the chain sealed and no witness, and a rerun refuses.
- Verify never looks for the witness.
- `_is_temp_copy` trusts `TMPDIR` and does not `realpath`.
- The placeholder check is a single exact string.
- Fix (I-01).

**F-22 — Tests.**
- `test_sync_refuses_public_remote` ends with a real push attempt to github.com. That is network use, and it can prompt on a TTY.
- `test_capture_browser_from_chrome_history_fixture` passes `None` and therefore scans the developer's real profiles, so `added == 1` fails on a workstation.
- `tests/test_chain_repair.py` appends `now` after 2026-11-02 fixture timestamps. The tests fail on any clock before that date.
- Untested: everything in F-01 to F-12, redaction shapes, the `--bot` matrix, status counts, Firefox capture, multi-process appends, `install.sh` and the hook.
- Fix (I-23 to I-31).

**F-23 — install.sh.**
- Piped to bash, `BASH_SOURCE[0]` is empty, `$0` is `bash`, and `HERE` becomes `$PWD`. Any `./gblog.py` is installed as a "local checkout".
- The download comes from a mutable `main` with no checksum. `py_compile` is not integrity.
- `GBLOG_ROOT` is persisted only if `PREFIX` was missing from PATH.
- The "added … to PATH" message prints even when no rc file exists.
- zsh is ignored.
- There is no Python version check, although the script requires 3.8+.
- The temp file leaks on failure.
- Non-interactive tool shells do not source `.bashrc`, so Bots may still not find `gblog`.
- Fix (I-41).

**F-24 — Anchors.** `anchor --bot X` replaces today's all-chain rollup with a one-chain rollup. A typo writes `anchors/<typo>.json`. FAIL chains without a seq break print `break None:None seq None->None`. Only the latest per-bot anchor survives locally. Fix (I-02, I-21).

**F-25 — Aliases.**
- `resolve` is single-pass in file order, so an alias on an earlier entry beats a later entry's slug. `alias_conflicts` nevertheless says "the slug wins".
- `add_alias` silently moves a variant away from another Bot, which re-homes its legacy chain in every merged report.
- `alias strict on` is a no-op while the registry is empty.
- Bot names collide with state files: `aliases` (`state/aliases.json`), `capture-files-x` (bot x's snapshot) and `x.alert` (bot x's alert file).
- `aliases.json` is written without a lock or fsync.
- Fix (I-19).

**F-26 — Archive.**
- No fsync of the `.gz` or its directory before the hash is chained. A power loss can leave a permanent "archived file missing".
- A missing or unreadable `--file` gives a traceback.
- Non-UTF-8 or binary content is stored verbatim with `redacted: false`, indistinguishable from "scanned, clean". README says the ledger "never points at a file that still holds a secret".
- `verify_archives` trusts `path` (absolute or `..`).
- Every verify re-hashes every archive; the cost is unbounded.
- "Identical content is stored once" is per Bot and day.
- Fix (I-20).

**F-27 — Exit codes.** `SystemExit("error: …")` exits 1, the same as verify FAIL, "not pushed" and any traceback. `OSError`, `BrokenPipeError` (`export | head`) and Ctrl-C produce tracebacks. Fix (I-07) plus a documented table (I-35).

**F-28 — Tail handling.** If the last line has no trailing newline (editor, manual restore), `_tail_record` parses it and `_append_line` glues the new record onto it, corrupting the chain. `_tail_record` reads the whole last file on every append. Fix (I-22).

**F-29 — Hygiene.** Logs are `0o644` and directories follow the umask. `sync` commits `state/*.lock`, `*.tmp` and capture snapshots. `last_sync` and the denied record are written after the commit, so the tree is always dirty. Fix (I-22).

**F-30 — Root selection.** With `GBLOG_ROOT` unset and `/workspace` not writable, gblog silently creates and uses `~/activity-log`. `ensure()` auto-initialises without a message, which also contradicts the routine's "report ledger missing instead of creating an empty one" (`anchor` and `report` create it). Fix (I-22, I-36).

**F-31 — Minor verify and CLI gaps.**
- `rec["bot"]` is not compared with the chain directory.
- Unexpected `*.jsonl` names take part in ordering. Sorting is lexicographic by name.
- Duplicate JSON keys or reformatted lines verify.
- `tail -n 0` prints the whole ledger.
- `log --type verify|sync|tune|archive` lets a Bot forge housekeeping records.
- Fix (I-21, I-13); the last point is documented only.

**F-32 — Portability.**
- `utcnow()` and `utcfromtimestamp()` are deprecated since 3.12.
- `_fsync_dir` raises on Windows, although the fcntl comment promises degraded operation there.

## 5. Out of scope / not recommended

- **Generalising `seal` to arbitrary breaks, or adding a `--force`/"accept truncation" mode.** The single pinned incident is the design; F-01 is fixed by making verify as strict as seal, not by loosening seal.
- **Auto-repair that rewrites, quarantines or rehashes log lines.** This includes trimming a torn final line. Recovery must stay append-only (state rebuild, spool replay) or restore from backup.
- **Signatures or HMAC with a key stored on the same computer.** The adversary is the Bot with the same file access. Use off-box anchors instead: heads posted in the conversation, and a remote with force-push disabled.
- **Changing the canonical JSON, the hash algorithm or schema `v`.** Any such change breaks existing ledgers.
- **Third-party dependencies or network-dependent tests.** That rules out `cryptography`, `filelock`, `pytest`, RFC 3161 timestamping and similar.
- **Dropping Python 3.8 or adding first-class Windows support.** Keep the degrade path from raising, nothing more.
- **`allow_abbrev=False`, removing `log --type` choices, or renaming `--jay-approval-id`.** These are compatibility breaks for little gain; document them instead.
- **Blocking appends on a full verify, or a database backend.** Per-append cost must stay O(1) and the JSONL files must stay human-readable.
- **Attributing shared-computer browser or file activity to individual Bots.** It is not knowable from the evidence; document the limit.

### 1. Executive summary

- **The honest-path core is sound.** Append is lock → `O_APPEND` → fsync → atomic state replace, and `verify` catches edited, deleted, duplicated and reordered lines.
- **Critical: the "pinned" break approval is enforced only in `seal`, not in `verify`.** Any chain can have a run of records deleted from one day file and be turned from `FAIL` into `PASS (1 approved break)`, exit 0, by appending a hand-made `break_ack` (F-01).
- **Ordinary accidents wedge a chain permanently.** A crash or full disk between the log fsync and the state replace, a back-dated, future-dated or malformed `--ts`, or a `sync` that runs while a state file is missing all end in exit 4 forever and/or a permanent `FAIL`. The only repair command is hard-wired to one incident (F-02, F-03, F-10, F-12).
- **Tamper evidence is weaker than the README states.** Deleting `state/<bot>.json` hides tail truncation, deleting a whole chain directory is invisible to `verify --all`, and `verify --bot <typo>` prints `OK … 0 records`. `anchor` never compares the chain with the previous anchor (F-04, F-05).
- **One malformed line takes down everything.** A non-object JSON line, invalid UTF-8, a corrupt gzip stream or a non-dict state file raises an uncaught exception that aborts `verify --all`, `anchor`, `report`, `status` and `tail` for every chain (F-06).
- **Secrets can leak.** Redaction misses env-var names (`DB_PASSWORD=…`, `AWS_SECRET_ACCESS_KEY=…`), `--password value` and `curl -u user:pass`, while the shell hook logs every command and `sync` pushes it (F-07). Combined with the README advice to auto-approve all `gblog` commands, `sync --remote` is an exfiltration and command-execution path, and `report --date` / `--ts` write files outside the ledger (F-08, F-09).
- **Agent-facing CLI friction loses records.** `task-end --summary` exits 2 and leaves the task open. `GBLOG_TASK` is honoured by `log` and `archive` but not `task-end`, `note` or `approval`. `verify`, `export`, `sync` and `anchor` skip alias resolution (F-13, F-14).
- **Tests miss the failure paths.** There are 35 tests (the README says 20), none covering concurrency, crash windows, malformed input or the forged ack. One test does a real `git push` to github.com and can hang on a TTY, and several pass only because the wall clock is later than 2026-11-02 (F-24). CI is Linux-only and never runs `install.sh` (F-26).
- **Docs overstate guarantees and are stale in places** (the pinned ack, "host/path only", test count, version labels, a routine step the code contradicts) (F-27).

### 3. Detailed findings

#### F-01 — `verify` honours any `break_ack`, in any chain (Critical)
`seal_break` pins the bot, coordinates and hashes. `verify` only checks that the single `break_ack` is well formed and describes the gap it finds. `Ledger.append` accepts `type: "break_ack"` (the test `test_wrong_ack_does_not_pass` relies on this), and the chain is unkeyed, so anyone with write access can hand-write the line.

Proof of concept on any chain `ops`: delete lines for seq 100–500 from one day file (tail and state untouched), then run:

```python
import gblog; L = gblog.Ledger()
L.append("ops", {"type": "break_ack", "jay_approval_id": "x", "break": L.verify("ops")["breaks"][0]})
```

`gblog verify --bot ops` now prints `PASS (1 approved break)` and exits 0. Unlike a full rewrite, this keeps every later hash intact, so heads quoted in replies, anchors and git history still match.

**Fix:** enforce the pin inside `verify` (I-01), using the same temp-copy and coordinate rule that `seal_break(copy_fixture=True)` already applies, so the existing fixture tests keep passing.

#### F-02 — Interrupted append wedges the chain (High)
The docstring correctly says a crash cannot leave state ahead of the file. It can leave the file ahead of state: SIGKILL, OOM, Ctrl-C in the shell hook, or `ENOSPC` while writing `state/<bot>.json.tmp`. After that:
- every append hits `_assert_tail_matches` and is refused with exit 4;
- `verify` reports `head does not match last record (state tampered or log truncated)`.

The log is the write-ahead record and state is a cache, so a tail that extends the state head by valid, linked records is not evidence of tampering.

**Fix:** roll state forward when the log is a valid extension of the state head, record the recovery in the new record, and downgrade the verify message to a warning in that case (I-03).

#### F-03 — Unvalidated `--ts` (High)
- An earlier day puts the record in a file that sorts first. `verify` then fails at the first record, and the next append is refused because the last file's tail no longer equals state.
- An earlier time on the same day gives a permanent `timestamp goes backwards`.
- A far-future value sends every later record to an earlier-sorting file.
- A different format such as `2026-11-16 10:00` breaks the lexicographic comparison.
- `today(ts)` is `ts[:10]`, so `--ts ../../a` or `--ts /tmp/abcde` writes a `.jsonl` outside `logs/`.
- A system clock stepping backwards produces the same permanent FAIL without any flag.

**Fix:** strict format; refuse a caller-supplied ts earlier than the tail; clamp when the system clock is behind; choose the file from the validated date (I-04).

#### F-04 — Truncation and deletion blind spots (High)
- `verify` detects a truncated tail only through `state.head`. Because `read_state` returns genesis for a missing or corrupt file, `rm state/ops.json` or writing garbage to it silences the check. After deletion, `append` silently continues from the truncated tail (the path `test_state_recovered_from_log_when_missing` exercises).
- `verify --all` iterates `logs/*`, so `rm -rf logs/ops state/ops.json` produces no line at all. With no chains left it prints `no bots logged yet` and exits 0.
- `verify --bot opz` verifies zero records and prints `OK`. With `--record` it also creates the chain.

**Fix:** build the set of known chains from logs, state and anchors; report a missing chain as FAIL; make an unknown `--bot` exit 2; mark state recoveries in the chain; check against the previous anchor (I-05, I-06).

#### F-05 — Anchors add no evidence (High)
`anchor()` records `resumed_from` but never checks that the previously anchored head is still in the chain.
- A chain that was truncated or fully re-hashed since the last anchor gets `ANCHOR OK`, and the old head is overwritten.
- `anchors/days/<today>.json` is rewritten on every run, so `gblog anchor --bot ops` leaves a rollup containing only `ops`.
- `anchor` calls `ensure()`, so on a missing ledger it creates an empty one. The daily routine says to report "ledger missing" instead.
- For a FAIL that is not a break, the CLI prints `break None:None seq None->None`.

**Fix:** I-06.

#### F-06 — Crash paths on malformed input (High)
- `json.loads` may return a list, number or null, and the code then calls `rec.get` or tests `"_corrupt" in rec`.
- Log files are opened as strict UTF-8.
- `verify_archives` does not catch `zlib.error`, which is not an `OSError`.
- `read_state` returns whatever JSON it finds, so a list or `"seq": "x"` crashes callers.
- `_break_shape_ok` calls `n["file"].startswith` outside its `try`.
- `aliases()` assumes dict shapes.
- `records()` sorts and compares `ts` assuming strings.

Each of these is a traceback that aborts all chains, contradicting "One FAIL chain does not drop the others".

**Fix:** treat anything unparsable as `_corrupt`, type-check, and isolate each chain (I-02).

#### F-07 — Redaction gaps (High)
The generic pattern needs `\b` on both sides of the keyword and a `:` or `=`. It therefore misses:
- `DB_PASSWORD=…`, `CLIENT_SECRET=…`, `MYSQL_PWD=…`, `ACCESS_TOKEN=…`, `AWS_SECRET_ACCESS_KEY=…`
- `--password hunter2`, `curl -u user:pass`, `Authorization: Basic …`
- token shapes such as `sk_live_…`, `glpat-…`, `npm_…`, `ya29.…`, `xoxe-…`

The shell hook passes whole commands as `--target`.

**Fix:** I-07. Detection remains pattern-based, and the docs must say so.

#### F-08 — `sync` remote handling (High)
- `--remote` silently replaces `origin`.
- Non-GitHub hosts and API failures are "unknown" and the push proceeds.
- `ext::`/`fd::` helper transports and remotes starting with `-` are not rejected.
- The refusal message and git stderr, which can contain `https://user:token@…`, are printed unredacted.
- `git push` has no timeout and no `GIT_TERMINAL_PROMPT=0`, so a credential prompt hangs a routine.
- A user with `commit.gpgsign=true` gets a failing or hanging commit.

README step 6 tells users to auto-approve all `gblog` commands, which turns `gblog sync --remote …` and `gblog archive --file ~/.ssh/id_rsa --no-redact` into approval bypasses.

**Fix:** I-08 for the code and I-23/I-24 for a narrower auto-approve rule.

#### F-09 — `report --date` / `--since` path injection (Medium)
`fname` is taken verbatim from the arguments. An absolute `--date` replaces the reports directory in `os.path.join`, and `..` escapes it.

**Fix:** validate as `YYYY-MM-DD` (I-04).

#### F-10 — Genesis state written over a missing or corrupt state (Medium)
The last loop of `sync` and the marker write in `capture_browser` call `read_state` and then `write_state`. When the file was missing or corrupt, this persists `{"seq":0,"head":"genesis", …}` for a chain that has records. The supported "recover from tail" path is thereby turned into a permanent tail mismatch, and a corrupt state file is destroyed as evidence.

**Fix:** never create or overwrite state outside `append` unless the current state loaded cleanly (I-03, I-08, I-12).

#### F-11 — `sync` commits rewrites silently (Medium)
The log is append-only, so any deleted or modified line under `logs/`, or a changed or deleted file under `archive/`, relative to `HEAD` is by definition tampering or corruption. Sync is the one place this can be detected against history, and it does not look.

Also:
- `git add … README.md` fails if the marker file was removed;
- `state/*.lock`, `*.tmp` and the `capture-files-*` snapshot are committed;
- the `sync` record stays `pending` for ever (the result lives only in `state.last_sync`);
- `git add` can snapshot a log and its state at different moments.

**Fix:** I-08.

#### F-12 — Tail-mismatch operations (Medium)
There is no command to list alerts, see whether a mismatch still exists, clear a resolved alert or replay spooled events. The existing test repairs by calling `write_state` by hand.
- `state/<bot>.alert.json` lives for ever.
- With the hook installed, every shell command creates a spool file.
- In `verify --all --record`, the `ledger.append` inside the loop raises `TailMismatchError`, so the chains after the affected one are never verified.
- `sync` aborts before committing if the `system` chain is the one affected.

**Fix:** I-09.

#### F-13 — Argument tolerance (Medium)
- `task-end --summary "…"` gives the argparse error and exit 2, and the task is never closed.
- `task-end`, `note` and `approval` ignore `$GBLOG_TASK`, although the SKILL tells agents to export it.
- `task-end` with no id at all writes a record that closes nothing, silently.
- `--outcome success|failed|done` exits 2.
- `--bot` is required even when `GBLOG_BOT` is set (the hook already uses that variable).

**Fix:** I-10.

#### F-14 — `--bot` handling is inconsistent (Medium)
`_resolve_bot` runs for seven commands. `report`, `tail`, `coverage` and `tune` use `canonical`. `verify`, `export`, `sync` and `anchor` use bare `safe_name`.
- `verify --bot "Chief of Staff"` checks the non-existent chain `Chief-of-Staff`.
- `verify --bot chief-of-staff` skips the `cos` and `cos-primary` chains.
- A non-ASCII display name exits with an error.

Bot names also collide with state files: `aliases` (`state/aliases.json`), `capture-files-<x>` and `<x>.alert`.

**Fix:** I-05, I-10.

#### F-15 — `status` miscounts (Medium)
`ledger.records(c)` expands `c` through `chains_for`, so iterating over a Bot's chains returns every record once per chain.
- `today` is inflated.
- `--chains` rows show merged numbers.
- Open tasks are computed from the last 7 local days only.
- `week` uses the local date while `today()` is UTC.
- The text output has no head column, although the README says status "shows chain heads".

**Fix:** I-11.

#### F-16 — `capture browser` (Medium)
- `datetime.utcnow().timestamp()` interprets a naive UTC value as local time. The test builds its fixture with the same expression, which masks the bug.
- Unreadable histories are skipped silently.
- The page title goes into `detail` (mailbox subjects, document names), while the README says "host/path only".
- With one shared browser profile, every Bot that runs capture imports the same visits into its own chain.

**Fix:** I-12 and docs.

#### F-17 — `capture files` (Medium)
- The snapshot is replaced non-atomically before the change records are appended.
- There is one snapshot per bot regardless of `--path`.
- A corrupt snapshot raises.
- `startswith(ledger.root)` also matches sibling directories.

**Fix:** I-12.

#### F-18 — Shell hook (Medium)
- The default bot is fixed at install. The second Bot's `--install` is a no-op, so its commands are logged under the first Bot.
- De-duplication by command text drops legitimate repeats.
- `--target "$cmd"` fails for commands starting with `-`.
- The hook only fires in interactive shells that source `~/.bashrc`. Whether agent tool shells do so is not verifiable from this repo, and the docs promise "every command".
- Each prompt pays a Python start, a full day-file read and several fsyncs.

**Fix:** I-12 and docs.

#### F-19 — Archive (Medium)
- A fixed `.tmp` name lets two concurrent identical archives interleave.
- There is no fsync, although the ledger line is fsynced.
- An existing file is trusted without re-hashing.
- `verify_archives` joins the recorded `path` without checking that it stays under `archive/`.
- The whole file is read into memory.
- Dedup is per bot and day, not global as the docstring implies.

**Fix:** I-13.

#### F-20 — Alias registry (Low)
- `add_alias` silently moves a variant away from another Bot.
- Case-insensitive duplicates across Bots are not flagged.
- A corrupt `aliases.json` is treated as empty: strict mode is off and every name counts as "known".
- An old chain created from a display name (`Kim-Biseo`) is not matched to the display name `Kim Biseo`.
- `save_aliases` takes no lock.

**Fix:** I-14.

#### F-21 — Tune and coverage (Low)

- `tune --bot X` overwrites `proposals.json` and the day report with only X's proposals.

#### F-22 — Exit codes (Low)

- 4 is a tail mismatch.

### 5. Out of scope / not recommended

- **Generalising `seal`** to arbitrary breaks or adding a "rehash" or "repair" command. The pinned, single-incident design is the safer one; F-01 closes the gap by making `verify` as strict as `seal`.
- **Keyed chains (HMAC or signatures).** The Bot shares the computer and would hold the key. This adds complexity without changing the threat model, and the remote git history remains the external witness.
- **Fail-closed pushes for unknown hosts by default.** That would break existing non-GitHub setups. It is documented instead, and could later be an opt-in `--require-private`.
- **Changing the record schema, hash canonicalisation or `SCHEMA_VERSION`**, renaming chains or migrating old variant chains.
- **`allow_abbrev=False`** or any removal of a currently accepted argument form.
- **Restricting `log --type` or `--source auto`.** Everything in the ledger is self-reported by design; document that coverage can be gamed rather than pretending otherwise.
- **Windows support** beyond not crashing in `_fsync_dir`. Without `flock` there is no safe concurrent append; state "POSIX only".
- **Third-party tooling** (pytest, linters, hypothesis) and any test that needs the network or a real browser profile.
- **Performance rewrites** such as seek-from-end tail reads or streaming verify, until a ledger demonstrates the need. The coverage index in I-14 is the only hot spot worth fixing now.
- **Automatic deletion or rotation** of logs, spool or alert files.
